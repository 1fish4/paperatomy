# 可视化原语

> 本文回答一个问题：**能不能把论文里的「问题」和「方法」动态演出来？**
>
> 结论：能，但不是"生成动画"，而是"从原语库里选型 + 填数据"。这两种做法的工程难度差一个数量级。

---

## 一、为什么不能"自动生成动画"

用户真正想要的是那种排序算法演示视频：数据在动，每一步发生了什么一目了然。

**那种动画是人写代码做出来的**，不是从文字生成的。要把论文的方法变成这样的动画，中间缺一步——把方法描述翻译成可执行程序。这是研究级难题，且不可能对所有论文成立。

但换个问法就有解了：

> 论文里的方法演示，形态是不是有限的？
> 演示所需的数据，论文里是不是本来就有？

两个答案都是"是"。所以真正的任务是**分类 + 填充**，不是**创作**。

## 二、设计原则

**原则一：AI 不画图，只选型和填空。**

每个原语是一个手写的前端组件，接收结构化参数。AI 的输出是一份"选型清单"：

```json
{
  "primitive": "pipeline",
  "params": { "stages": [...] },
  "evidence": [{ "page": 4, "quote": "..." }]
}
```

好处：
- 画法固定 → 样式统一、质量可控、不会每次长得不一样
- 加一种可视化 = 加一个组件，**别人可以贡献**（可复用的第二个入口）
- 出问题能定位：是选错了原语，还是填错了参数

**原则二：没有原文依据，宁可不演。**

每个原语必须带 `evidence`。如果论文没给收敛曲线、没给具体例子，对应的原语直接跳过，**不允许模型编造数据来凑一张好看的图**。

这条比"覆盖更多论文"重要。一个编造的动画比没有动画更糟。

**原则三：一个原语只演一件事。**

不要把"问题 + 方法 + 结果"塞进同一个动画。观众一次只能跟一条线。

## 三、第一批原语

| 原语 | 演什么 | 数据来源 | 适用论文 | 状态 |
|------|--------|---------|---------|:---:|
| `pipeline` | 方法整体流程，逐段点亮，每段配「做什么 / 为什么必须」 | 方法章节的步骤描述 | 几乎所有方法类论文 | ✅ |
| `example` | 用论文里的具体例子走一遍：输入 → 卡点 → 处理 → 输出 | Running example / toy example | 有示例图的论文 | ✅ |
| `taxonomy` | 分类框架逐层展开 | 综述的分类体系、分类表 | 综述、体系性论文 | ✅ |
| `iteration` | 指标随迭代变化的动态曲线，可叠加多条基线 | 收敛图、训练曲线 | 优化、训练类 | 三期 |
| `comparison` | 不同方法的指标逐条对抗（条形竞赛） | 结果表格 | 实验类 | 三期 |
| `tree` | 搜索树 / 决策树逐步扩展，可高亮剪枝 | 算法描述 | 搜索、规划、决策树 | 三期 |
| `matrix` | 矩阵 / 热力图逐帧变化 | 注意力图、混淆矩阵 | 深度学习 | 三期 |

> `taxonomy` 是二期加进来的。原计划二期只做 `pipeline` + `example`，
> 但这两个原语对**综述**几乎全空——综述没有方法流程，往往也没有 toy example。
> 而综述恰恰是读得最多、最难读完的一类。所以补了 `taxonomy`：
> 综述的核心贡献就是它的分类框架，把这个框架演出来，等于把整篇文章的骨架演出来。

### 三个核心原语的详细规格

#### `example` —— 演「问题是什么」

价值最高。看不懂往往不是因为概念难，而是因为抽象；一个具体例子走一遍，胜过十段定义。

```json
{
  "primitive": "example",
  "title": "冷启动推荐为什么难",
  "params": {
    "scenario": "新用户刚注册，没有任何历史行为",
    "steps": [
      { "state": "候选池有 100 万篇文章", "issue": "不知道该推哪一篇" },
      { "state": "尝试按热度推荐", "issue": "所有人看到的内容一模一样" },
      { "state": "本文的做法：用注册时选的 3 个兴趣标签初始化", "issue": null }
    ]
  }
}
```

前端表现：逐步骤推进，`issue` 非空时该步标红并停留，让"卡在哪"被看见。

**校验上有一条硬规则**：所有步骤的 `issue` 都为空时，这个原语直接判不合法。
没有卡点的「例子」等于复述流程，不做比做更好。

#### `pipeline` —— 演「怎么解决」

```json
{
  "primitive": "pipeline",
  "title": "两阶段检索",
  "params": {
    "stages": [
      { "name": "粗排", "what": "从百万候选筛出 1000 条", "why": "全量精排成本过高" },
      { "name": "精排", "what": "对 1000 条逐条打分", "why": "候选少，可用重模型" }
    ]
  }
}
```

前端表现：连线按顺序点亮，每段展开时下方显示「做什么 / 为什么必须」。

**没有 `why` 的阶段不报错，但要显式提示**——它往往说明这一步的必要性在论文里没讲清，
应当回到「值得追问的问题」里，而不是让前端假装它很合理。

#### `taxonomy` —— 演「领域怎么分」

```json
{
  "primitive": "taxonomy",
  "title": "三层分类框架",
  "params": {
    "root": {
      "name": "Resource-efficient Foundation Models",
      "children": [
        { "name": "Architecture", "what": "改结构本身",
          "children": [{ "name": "Efficient Attention" }] },
        { "name": "Algorithm", "what": "改训练与推理过程",
          "children": [{ "name": "Quantization" }] }
      ]
    }
  }
}
```

前端表现：树状结构，按层展开，每层告诉你"这一层有几个分类"。

约束：**深度最多 3 层，总节点不超过 20 个**。超过就不是"一眼看懂"，而是另一篇论文。

## 四、覆盖率的诚实预估

| 论文类型 | 预计覆盖率 | 说明 |
|---------|-----------|------|
| 方法类（CS / 工程） | ~50% | `pipeline` + `example` 能覆盖大半 |
| 数学建模 / 系统设计 | 较高 | 流程明确，`pipeline` 天然适配 |
| 纯理论（定理证明） | 接近 0 | 没有流程可演，不在范围内 |
| 纯实验 / 综述 | 低 | 价值在数字与结论，不在机制 |

**不追求全覆盖。** 一个原语演得准，比六个原语都演得含糊有价值。

## 五、分期

| 期 | 内容 |
|----|------|
| 一期 | 结构图（模板抽取的静态结果）——先让产品成立 |
| 二期 | `pipeline` + `example` 两个原语——直接回应「问题是什么 / 怎么解决」 |
| 三期 | `iteration` / `comparison` / `tree` / `matrix` |
| 之后 | 开放组件协议，允许社区贡献原语 |

**一期不做可视化**，因为结构图本身就是"读得懂"的最低门槛。原语是增值，不是前提。
